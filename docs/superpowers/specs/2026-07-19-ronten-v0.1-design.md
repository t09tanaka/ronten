# ronten v0.1 — Design

A concern-based PR review viewer. A coding agent decomposes its completed changes into
"concerns", a human reviews each concern in the browser, and the review result is returned
to the agent as machine-readable JSON. Shipped as a single CLI binary.

Name frozen: **ronten** (crates.io and npm both available as of 2026-07-19; `prsm` taken on
both, `concern` taken on npm).

## 1. Design principles

1. **Daemonless.** One review session = one CLI invocation. A local HTTP server exists only
   while the process is alive and disappears on submission or process exit. No state files,
   sockets, or background services.
2. **Agent-agnostic.** The contract is "pass JSON, receive JSON". Agents can self-discover
   the contract via `ronten schema`.
3. **Diff truth comes from git.** The agent supplies only concerns and location mappings.
   ronten computes the diff itself from `git diff <base>...HEAD`. An agent cannot hide or
   fake changes.
4. **Single binary.** Rust, with frontend assets (Svelte build output) embedded. Zero
   runtime dependencies beyond `git` itself.
5. **Concurrency by process isolation.** Parallel worktrees with simultaneous review
   sessions are first-class: each session has its own process and port, no shared ledger,
   no locks.

## 2. Lifecycle

```
agent                        ronten                            human
  |                            |                                 |
  |-- run `ronten review` ---->|                                 |
  |   (base ref + concerns)    |-- compute git diff              |
  |                            |-- resolve mappings, detect      |
  |                            |   unmapped hunks                |
  |                            |-- serve HTTP on 127.0.0.1:0     |
  |                            |-- print URL / open browser ---->|
  |        (blocked)           |                                 |-- review per concern
  |                            |<---------- submit --------------|
  |<-- result JSON on stdout --|                                 |
  |<-- exit code --------------|  (process exits, server gone)   |
  |-- interpret result, fix    |                                 |
```

## 3. CLI

### 3.1 `ronten review`

```
ronten review --base <ref> --concerns <file|-> [options]
```

| Option | Default | Description |
|---|---|---|
| `--base <ref>` | required | Comparison base; computes `git diff <ref>...HEAD` |
| `--concerns <path>` | required | Concerns JSON path; `-` for stdin |
| `--out <path>` | none | Also write result JSON to a file (in addition to stdout) |
| `--port <n>` | `0` (OS-assigned) | Bind port, for fixed allocation (e.g. portool) |
| `--no-open` | false | Do not auto-open the browser; print URL only |
| `--title <s>` | branch name | Session display name |
| `--timeout <dur>` | none | Exit 3 if no submission within the duration (e.g. `30m`) |

Output separation is strict: human-facing logs go to stderr
(`Review session: http://127.0.0.1:PORT/r/TOKEN`), machine-readable data (the result JSON)
goes to stdout only.

### 3.2 Exit codes

| code | meaning |
|---|---|
| 0 | all concerns approved |
| 1 | one or more request-changes |
| 2 | reviewer aborted |
| 3 | timeout |
| 10+ | input errors (invalid JSON, unresolvable base, outside a git repo, empty diff, …) |

### 3.3 `ronten schema`

Prints the JSON Schemas for input (concerns) and output (result) to stdout;
`--input` / `--output` for one at a time. Schemas are generated from the serde types via
`schemars`, so they can never drift from the implementation.

### 3.4 `ronten demo`

Launches the UI with an embedded sample diff and concerns (no git required). For README
GIFs and first-touch exploration.

## 4. Input: concerns JSON

```jsonc
{
  "version": 1,
  "summary": "Introduce auth middleware and adjust route definitions",
  "concerns": [
    {
      "id": "auth-core",                 // unique slug
      "title": "Auth middleware core",
      "description": "Validates JWT … (agent's intent/rationale, markdown allowed)",
      "risk": "high",                    // high | medium | low
      "locations": [
        { "path": "src/middleware/auth.ts" },                          // whole file
        { "path": "src/routes/index.ts", "side": "new", "start": 10, "end": 42 }  // line range
      ]
    }
  ]
}
```

### 4.1 Mapping resolution rules

- The diff is split into hunks; each hunk is tested for intersection against every
  location. A hunk is shown under **every** concern it intersects (overlapping membership
  is allowed — cross-cutting concerns genuinely span multiple concerns).
- `side: "new"` refers to post-change line numbers, `"old"` to pre-change (for
  deletion-only hunks). Omitting `start`/`end` means the whole file.
- **Any hunk matching no concern is placed into an auto-generated "unmapped" concern**
  (`_unmapped`). It is rendered in a warning color and requires a verdict like any other
  concern. Agent mapping omissions are always surfaced to the human — this is the core of
  the trust model.
- Locations pointing at nonexistent paths or out-of-range lines are not errors; they are
  recorded as warnings in the result JSON so minor agent drift never blocks a review.
- Unknown fields in the concerns JSON are ignored without warnings (forward
  compatibility; no metadata field in v0.1).

## 5. Output: result JSON

```jsonc
{
  "version": 1,
  "decision": "request-changes",         // approve | request-changes | abort
  "concerns": [
    {
      "id": "auth-core",
      "verdict": "request-changes",      // approve | request-changes | comment
      "comments": [
        {
          "path": "src/middleware/auth.ts",
          "side": "new",
          "line": 27,
          "body": "No log on the token-expiry branch"
        }
      ]
    },
    { "id": "_unmapped", "verdict": "approve", "comments": [] }
  ],
  "general_comments": ["Overall, …"],
  "warnings": ["location out of range: src/routes/index.ts:120-140"],
  "started_at": "…", "submitted_at": "…"
}
```

`decision` is derived from the verdicts (any request-changes ⇒ request-changes). Agents can
feed `concerns[].comments` directly into their fix loop.

## 6. UI (localhost HTML, all copy in English)

- Left pane: concern list with risk badges, reviewed checkmarks; unmapped shown in warning
  style.
- Main pane: selected concern's description as header, diff filtered to that concern's
  hunks. Hunks shared with other concerns carry a badge; clicking it jumps to the other
  concern.
- Per-concern verdict buttons (approve / request-changes / comment); click a line number
  for an inline comment.
- Submit is disabled until every concern has a verdict. Abort is always available (exit 2).
- Keyboard-first: `j/k` concern navigation, `a` approve, `x` request-changes, `c` comment,
  `Enter` submit confirmation. A full review pass must be possible without a mouse.
- Minimal-dependency Svelte build; diff rendering is our own. No virtual scrolling in
  v0.1 — only one concern's hunks render at a time, and large hunks are collapsed by
  default (click to expand). Syntax highlighting: lightweight language detection if cheap,
  otherwise plain.

## 7. Security

- Bind `127.0.0.1` only.
- Random per-session token in the URL path (`/r/<128-bit>`); all API routes require it.
  Prevents same-machine snooping/forged submissions via port scanning.
- Submission is accepted once per process lifetime; subsequent attempts get 409.

## 8. Technical design

### 8.1 Stack

- **Rust + axum + tokio** for the HTTP server (JSON extractors, graceful shutdown, room
  for SSE later).
- **clap** for the CLI (`review` / `schema` / `demo`).
- **serde + schemars** for models and generated JSON Schemas.
- **Svelte 5 + Vite** frontend, built to static assets and embedded with `rust-embed`.
  During development, Vite dev server proxies API calls to the Rust process.

### 8.2 Diff acquisition

Run `git diff <base>...HEAD --no-color --unified=3` as a subprocess and parse the unified
diff with a small in-house parser. Rationale: git presence is a given (the tool operates on
git repos), the `...` merge-base semantics match git exactly, and it avoids linking
libgit2/gix. Binary changes and renames are represented as hunk-less file entries.

### 8.3 Module layout

```
src/
  main.rs      — CLI parsing, dispatch, exit-code mapping
  model.rs     — serde types for concerns/result + schemars derives
  gitdiff.rs   — git invocation + unified diff parsing → FileDiff/Hunk
  mapping.rs   — hunk × location intersection, _unmapped synthesis, warnings
  session.rs   — session state (diff + concerns + Mutex<Draft>)
  server.rs    — axum routes, token check, static assets
  demo.rs      — builds a session from embedded fixtures (no git)
frontend/      — Svelte app (npm project; build output embedded)
```

### 8.4 HTTP API (under `/api/<token>/`, 127.0.0.1 only)

- `GET  session` — diff, concerns, resolved hunk mapping, current draft in one payload.
- `PUT  draft` — full replacement of in-progress verdicts/comments, held in process
  memory. Page reloads restore it; with multiple tabs, last write wins.
- `POST submit` — server-side re-validation that every concern has a verdict → finalize
  result JSON → notify main via oneshot channel → process exits. Second call: 409.
- `POST abort` — exit 2.

`main` waits with `tokio::select!` on: submit/abort notification, Ctrl-C, and the optional
timeout; then prints result JSON to stdout (submit only) and exits with the mapped code.

### 8.5 Error handling

- Input errors are distinguished as exit 10, 11, 12, … with human-readable stderr
  messages: invalid concerns JSON, unresolvable base ref, not a git repository, empty
  diff (nothing to review).
- Location warnings (missing path, out-of-range lines) never block; they surface in the UI
  and in `result.warnings`.

## 9. Testing

- **Rust unit tests**: mapping (intersection, `_unmapped`, out-of-range warnings) and the
  diff parser, using string-literal diff fixtures.
- **Rust integration tests**: build a real git repo in a tempdir, launch the binary with
  `--no-open`, drive the HTTP API programmatically (get session, put draft, submit /
  abort / let it time out), assert on stdout JSON and exit codes. Covers all exit paths.
- **Frontend**: keep logic thin; a few Vitest unit tests (e.g. keyboard navigation state).
  E2E is manual via `ronten demo` in v0.1.

## 10. Non-goals (v0.1)

- GitHub/GitLab comment publishing or PR integration (future `ronten publish`).
- Review history persistence, multi-reviewer, authentication.
- Editing the diff (fixes are the agent's job).
- Native Windows (WSL is fine; targets are macOS/Linux).
- Virtual scrolling (revisit in v0.2 if collapsed-hunk rendering proves insufficient).
- Agent self-reported metadata fields in concerns JSON (unknown fields are ignored,
  leaving room to add later).

## 11. Agent integration patterns (documented in README)

1. **Blocking**: `result=$(ronten review …)` — for environments with extendable command
   timeouts.
2. **Background + polling**: `ronten review --out result.json … &` and poll for
   `result.json` — for agent shells with hard timeouts (e.g. Claude Code bash). Still a
   session process, not a daemon.

## 12. Future connection points

- portool: fixed port allocation via `--port`.
- Kiri: open the session URL in an IDE webview.
- `ronten publish`: result JSON → GitHub PR review comments.
